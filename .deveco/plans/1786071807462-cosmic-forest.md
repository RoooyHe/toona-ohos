# Goal
Kill the `ServiceRegistry` God Object. Replace it with two layers:
1. **ServiceLocator** — thin AppStorage-backed singleton accessor (one key per service, no business logic)
2. **Narrow facades** — per-consumer-cluster objects that expose only the services a page needs, hiding the locator entirely

Each page gets a facade tailored to its needs. No page ever sees all 17 services.

# Scope / Non-goals

**In scope:**
- Create `ServiceLocator.ets` with AppStorage-backed getters/setters for all 17 services
- Create 5 narrow facade classes grouped by consumer cluster
- Update `AppNavigation.ets` (composition root) to wire everything
- Update all 13 page consumers + 1 ViewModel to use facades instead of ServiceRegistry
- Keep `ServiceRegistry` as a deprecated thin delegate during transition

**Out of scope:**
- Changing service constructors or dependency wiring between services
- Adding new features or changing behavior
- Refactoring page component internals (only changing dependency acquisition)

## Constraints
- **ArkTS strict mode**: No `any`, no `unknown`, no destructuring, no spread, all object literals need type context
- **AppStorage pattern**: Already used by ServiceRegistry — `AppStorage.setOrCreate<T>(key, value)` / `AppStorage.get<T>(key)`
- **No circular deps**: Services don't import ServiceRegistry — must not import ServiceLocator or facades either
- **Struct field initializers**: Fields like `private scanManager: ScanManager = ServiceRegistry.getCurrent().getScanManager()` must still work at declaration time

# Design

## Layer 1: ServiceLocator (AppStorage-backed per-service singletons)

```typescript
// services/ServiceLocator.ets
export class ServiceLocator {
  // One AppStorage key per service, prefixed 'svc_'
  // set*() called from AppNavigation composition root
  // get*() called from facades or directly for simple consumers

  static setAuthManager(mgr: AuthManager): void {
    AppStorage.setOrCreate<AuthManager>('svc_authManager', mgr);
  }
  static getAuthManager(): IAuthManager {
    const mgr: AuthManager | undefined = AppStorage.get<AuthManager>('svc_authManager');
    if (!mgr) { throw new Error('AuthManager not initialized'); }
    return mgr;
  }
  // ... same for all 17 services
}
```

## Layer 2: Narrow facades

Each facade is a class whose constructor reads from ServiceLocator. Pages create a facade instance in `aboutToAppear()` (or at field init for simple cases). The facade exposes only what that cluster of consumers needs.

### SessionContext
**Who uses it**: LoginPage, RegisterPage, MainPage (logout only)

```typescript
// services/facades/SessionContext.ets
export class SessionContext {
  private authManager: IAuthManager = ServiceLocator.getAuthManager();
  private userAuthManager: UserAuthManager = ServiceLocator.getUserAuthManager();

  getAuthManager(): IAuthManager { return this.authManager; }
  getUserAuthManager(): UserAuthManager { return this.userAuthManager; }
  getSession(): Session | null { return this.authManager.getSession(); }
  getHomeserver(): string { return this.authManager.getHomeserver(); }
  async setHomeserver(url: string): Promise<void> { await this.authManager.setHomeserver(url); }
  async checkHomeserverVersion(): Promise<boolean> { return await this.authManager.checkHomeserverVersion(); }
  async login(userId: string, password: string): Promise<Session> { return await this.authManager.login(userId, password); }
  async register(username: string, password: string): Promise<void> { return await this.authManager.register(username, password); }
  async logout(): Promise<void> { await this.authManager.logout(); }
  async authenticateWithFace(): Promise<boolean> { return await this.userAuthManager.authenticateWithFace(); }
}
```

### SettingsPage special case

SettingsPage uses both `UserContext` and `DeviceContext` — it creates both in `aboutToAppear()`. This is fine; it's still better than calling `ServiceRegistry.getCurrent()` 15 times.

### Simple consumers that only need 1-2 services

Pages that only access 1-2 services (SearchPage, RoomSettingsPage, SpaceDetailPage, NotificationSettingsPage, etc.) can either:
- Use the `RoomContext` facade (if it covers their needs), OR
- Call `ServiceLocator.getX()` directly (for the simplest cases like NotificationSettingsPage which only needs PushManager)

**Decision**: For single-service consumers, use `ServiceLocator.getX()` directly. For multi-service consumers, use the appropriate facade. This avoids over-engineering the simple cases.

### MainPage refinement

MainPage needs SyncManager (not in RoomContext) and UserManager (not in RoomContext). Options:
1. Add SyncManager to RoomContext → makes it less narrow
2. MainPage uses RoomContext + direct ServiceLocator calls for extras → acceptable
3. Create a MainContext facade → most aligned with the "facades everywhere" approach

**Decision**: Create a `MainContext` facade specifically for MainPage since it's a unique cluster (sync + rooms + tags + user profile). This is the deepest facade win.

```typescript
// services/facades/MainContext.ets
export class MainContext {
  private syncManager: ISyncManager = ServiceLocator.getSyncManager();
  private roomManager: IRoomManager = ServiceLocator.getRoomManager();
  private roomTagManager: RoomTagManager = ServiceLocator.getRoomTagManager();
  private authManager: IAuthManager = ServiceLocator.getAuthManager();
  private userManager: UserManager = ServiceLocator.getUserManager();

  getSyncManager(): ISyncManager { return this.syncManager; }
  getRoomManager(): IRoomManager { return this.roomManager; }
  getRoomTagManager(): RoomTagManager { return this.roomTagManager; }
  getAuthManager(): IAuthManager { return this.authManager; }
  getUserManager(): UserManager { return this.userManager; }
}
```

## RoomDetailViewModel refactor

Currently: `constructor(roomId: string, roomName: string, registry: ServiceRegistry)`

After: `constructor(roomId: string, roomName: string, context: MessagingContext)`

The ViewModel already extracts individual services from the registry in its constructor — this just changes the source from registry.getX() to context.getX().

## ServiceRegistry deprecation

`ServiceRegistry.init()` stays working by delegating to `ServiceLocator.set*()`. All `getX()` methods delegate to `ServiceLocator.getX()`. Marked `@deprecated`. No external code should use it after this PR.

# Risks And Compatibility

- **Field initializer timing**: Facades use `ServiceLocator.getX()` in field initializers. This works because `AppNavigation.aboutToAppear()` runs first and populates AppStorage. Same risk as current `ServiceRegistry.getCurrent()` at field-init time.
- **AppStorage type erasure**: `AppStorage.get<T>()` returns `T | undefined`. The `if (!mgr) throw` pattern handles this — same as current ServiceRegistry.
- **Facade field-init ordering**: In ArkTS struct declarations, field initializers run in declaration order. A facade created at field-init time (e.g., `private ctx: RoomContext = new RoomContext()`) will call ServiceLocator.get*() during struct construction. This is fine as long as ServiceLocator has been populated first.
- **Backward compat**: ServiceRegistry delegates to ServiceLocator, so both access paths return the same instances.
